# A1. Добавить себя в docs/team.md

**Уровень:** L0 · **Время:** 20 минут · **Кому:** каждому, это первая задача

**Зачем эта задача.** Не ради текста в файле. Цель — один раз пройти весь путь `ветка → коммит → PR → ревью → мерж` на изменении, которое физически невозможно сломать. Дальше этот путь будет на автомате.

## Шаги

**1. Возьми задачу на доске.** Найди её в колонке `Ready`, справа в поле `Assignees` поставь себя, перетащи карточку в `In Progress`. Запомни номер issue (например, `#25`).

**2. Создай ветку от свежего main:**

```bash
git switch main
git pull
git switch -c docs/25-add-me-to-team
```

Разбор имени ветки: `docs/` — тип изменения (документация), `25` — номер твоей задачи, дальше — краткая суть латиницей.

**3. Открой `docs/team.md`** в редакторе. Найди таблицу «Состав», скопируй строку-образец и заполни своими данными:

```markdown
| Иван Петров | [@ivanpetrov](https://github.com/ivanpetrov) | Разработчик A | signing, backoff, matcher | UTC+3 |
```

Не знаешь свой часовой пояс в формате UTC — загугли «мой часовой пояс UTC». Москва — UTC+3.

Ниже в разделе «О нас» добавь абзац о себе: опыт, что хочешь прокачать. Пара предложений, свободным текстом.

**4. Посмотри, что изменил** (полезная привычка — всегда смотреть перед коммитом):

```bash
git status        # какие файлы тронуты
git diff          # что именно изменилось (выйти — клавиша q)
```

**5. Сохрани и отправь:**

```bash
git add docs/team.md
git commit -m "docs: add Ivan Petrov to team"
git push -u origin docs/25-add-me-to-team
```

**6. Открой PR.** После push терминал напечатает ссылку `https://github.com/.../pull/new/docs/25-...` — открой её. Заполни шаблон, в первой строке напиши `Closes #25` (подставь свой номер). Нажми **Create pull request**.

**7. Дождись ревью.** Придут комментарии — правишь в той же ветке, снова `git add` + `commit` + `push`. PR обновится сам, пересоздавать не надо.

**8. После мержа** подчисти у себя:

```bash
git switch main
git pull
```

## ⚠️ Типичные ошибки

| Ошибка | Что произошло | Как исправить |
|---|---|---|
| `git push` отклонён с «rule violations» | пытаешься пушить прямо в `main` | работай в своей ветке, см. шаг 2 |
| В PR куча чужих изменений | ветка создана не от свежего `main` | `git switch main && git pull`, создай ветку заново, перенеси правку руками |
| Забыл `Closes #25` | задача не закроется сама после мержа | отредактируй описание PR, допиши строку |

## ✅ Готово, когда

- [ ] Твоя строка есть в таблице `docs/team.md`
- [ ] PR смержен, ветка удалена автоматически
- [ ] Карточка на доске уехала в `Done`

# A2. Makefile: цель `make help`

**Уровень:** L0 · **Время:** 30 минут

**Зачем.** Чтобы новичок мог набрать `make help` и увидеть все доступные команды с описаниями, а не читать Makefile глазами.

## Как это работает (принцип)

Идея: к каждой цели дописывается комментарий с двумя решётками, а `help` вытаскивает их регулярным выражением и печатает списком.

```makefile
test: ## прогнать все тесты
	go test ./...
      ↑
      это описание попадёт в вывод help
```

## Шаги

**1.** Проверь, есть ли уже цель `help` в `Makefile`. Если есть — задача сводится к тому, чтобы **дописать комментарии `##` ко всем остальным целям**, у которых их нет.

**2.** Если цели `help` нет — добавь её. Стандартный приём: `grep` находит все строки вида `имя:` с комментарием `##`, `awk` красиво форматирует.

**3.** Сделай `help` целью по умолчанию, чтобы просто `make` без аргументов показывал справку:

```makefile
.DEFAULT_GOAL := help
```

**4.** Добавь `help` в список `.PHONY` (объяснение — в грабли ниже).

**5.** Проверь:

```bash
make help
make          # должно показать то же самое
```

## ⚠️ Главная грабля Makefile

**Отступ перед командой — это символ табуляции, а не пробелы.** Если поставить пробелы, make выдаст загадочное `missing separator`. Включи в редакторе отображение невидимых символов (VS Code: `View → Render Whitespace`), чтобы видеть разницу.

**Что такое `.PHONY`.** Это список целей, которые не являются именами файлов. Если в проекте появится файл или папка с именем `test`, make решит, что цель `test` уже «собрана», и откажется её выполнять. `.PHONY: test` снимает эту проблему.

## ✅ Готово, когда

- [ ] `make help` печатает все команды с описаниями
- [ ] Просто `make` показывает справку
- [ ] У каждой существующей цели есть комментарий `##`
- [ ] `help` есть в `.PHONY`

# A3. Godoc-комментарии в пакете domain

**Уровень:** L0→L1 · **Время:** 40 минут · **Зависит от:** задачи #11 (скелет)

**Зачем.** В Go комментарии к экспортируемым (публичным) типам — часть стандарта. По ним генерируется документация, их показывает редактор при наведении мышью.

## Правило Go (запомни, пригодится везде)

Комментарий начинается **с имени того, что описывает**, и пишется прямо над ним без пустой строки:

```go
// Message описывает одну доставку события конкретному получателю.
// Одно событие порождает столько Message, сколько у приложения
// подходящих подписок.
type Message struct {

// StatusPending означает, что сообщение ждёт в очереди
// и будет захвачено воркером, когда наступит NextAttemptAt.
StatusPending MessageStatus = "pending"
```

⚠️ Не «Это структура сообщения», а «Message описывает…». Именно с имени.

## Шаги

1. Открой `docs/TZ.md` §6.1 — там список всех типов пакета `domain` с объяснением, что каждый значит.
2. Пройди по файлам `internal/domain/*.go`.
3. Каждому **экспортируемому** (с заглавной буквы) типу, константе и переменной ошибки — комментарий по правилу выше. Приватные (с маленькой буквы) можно не комментировать.
4. Не пересказывай очевидное. Плохо: `// ID это ID`. Хорошо: `// ID — уникальный идентификатор сообщения, он же уходит получателю в заголовке X-Hookline-Id для дедупликации.`
5. Проверь себя — посмотри, как это выглядит в документации:

```bash
go doc ./internal/domain
go doc ./internal/domain Message
```

## ✅ Готово, когда

- [ ] У всех экспортируемых типов и ошибок в `domain` есть комментарии
- [ ] Каждый начинается с имени сущности
- [ ] `go vet ./...` молчит
- [ ] `go doc ./internal/domain` читается как нормальная документация

# B1. backoff — калькулятор задержки ретрая

**Уровень:** L1 · **Время:** 2–3 часа · **Спецификация:** `docs/TZ.md` §6.3

⭐ **Лучшая первая задача с кодом.** Чистая функция: ни базы, ни сети, ни docker. Всё, что нужно — Go и тесты.

## Что нужно сделать простыми словами

Написать функцию, которая отвечает на вопрос: «доставка провалилась в N-й раз, через сколько пробовать снова?».

Ответ растёт вдвое с каждой попыткой: 5 секунд, 10, 20, 40… — но не бесконечно, есть потолок. И в конце к результату применяется случайный разброс.

🧠 **Зачем разброс (джиттер).** Представь: тысяча сообщений провалилась одновременно, потому что получатель упал. Без разброса все повторятся ровно через 5 секунд — единым залпом, и добьют сервер, который только поднимался. С разбросом они размажутся по интервалу. Это называется **thundering herd**, и это классический вопрос на собеседовании.

## Подготовка

```bash
git switch main && git pull
git switch -c feat/19-backoff-calculator
mkdir -p internal/backoff
```

Создай два файла: `internal/backoff/backoff.go` и `internal/backoff/backoff_test.go`.

⚠️ Файл с тестами **обязан** заканчиваться на `_test.go` — иначе Go его не увидит.

## Шаг 2. Сначала тест, потом реализация

Так проще: ты сразу описываешь, чего хочешь, и видишь прогресс.

**Табличный тест** — стандарт де-факто в Go. Устроен так: список случаев, потом цикл по ним.

```go
package backoff

import (
	"math/rand"
	"testing"
	"time"
)

func TestNext_НеПревышаетПотолок(t *testing.T) {
	cfg := Config{Base: 5 * time.Second, Cap: 6 * time.Hour}
	rnd := rand.New(rand.NewSource(42)) // фиксированный seed = воспроизводимо

	tests := []struct {
		name    string
		attempt int
		maxWant time.Duration // результат не должен превышать это
	}{
		{"первая попытка", 0, 5 * time.Second},
		{"вторая", 1, 10 * time.Second},
		{"третья", 2, 20 * time.Second},
		{"большая", 10, 6 * time.Hour},
		{"огромная — не должно переполнить", 100, 6 * time.Hour},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got := Next(tc.attempt, cfg, rnd)
			if got < 0 {
				t.Fatalf("отрицательная задержка: %v", got)
			}
			if got > tc.maxWant {
				t.Fatalf("задержка %v больше допустимой %v", got, tc.maxWant)
			}
		})
	}
}
```

Запусти — тест должен **упасть** (функция возвращает 0, но 0 ≤ maxWant, так что может и пройти; добавь проверку роста позже):

```bash
go test ./internal/backoff/ -v
```

## Шаг 3. Реализуй по алгоритму

Алгоритм из ТЗ §6.3, по шагам:

1. Если `attempt` меньше нуля — считай как ноль.
2. Посчитай `delay = Base × 2^attempt`. В Go умножение на степень двойки — это сдвиг: `cfg.Base << attempt`.
3. ⚠️ **Главная грабля:** при большом `attempt` сдвиг переполнит `int64` и даст **отрицательное** число. Защитись: если `attempt` больше 62 или результат получился ≤ 0 — сразу используй `Cap`.
4. Если `delay > cfg.Cap` — возьми `cfg.Cap`.
5. Примени full jitter: верни случайное значение от 0 до `delay` включительно. Пригодится `rnd.Int63n(n)` — он возвращает случайное от 0 до n-1.
6. ⚠️ `Int63n` **паникует**, если аргумент ≤ 0. Учти это.

Пиши сам — тут всего десяток строк, и именно они дадут понимание.

## Шаг 4. Дополни тесты

Из ТЗ §6.3 обязательны:

1. **Воспроизводимость.** Два прогона с одинаковым seed дают одинаковые результаты.
2. **Диапазон.** Для attempt от 0 до 20 результат всегда в `[0, min(Cap, Base×2^attempt)]`.
3. **Не паникует** при attempt = 100.
4. **Не паникует** при `Base = 0`.
5. **Растёт.** Прогони по 1000 раз для attempt=1 и attempt=5, посчитай средние — второе должно быть заметно больше.
6. **Покрытие 100%.**

Проверить покрытие:

```bash

# посмотреть, какие строки не покрыты:
go test ./internal/backoff/ -coverprofile=cover.out
go tool cover -html=cover.out
```

# B2. matcher — сопоставление типов событий

**Уровень:** L1 · **Время:** 2 часа · **Спецификация:** `docs/TZ.md` §6.4

## Что нужно сделать простыми словами

Событие имеет тип: `order.created`. Подписка задаётся шаблоном: `order.*`. Нужна функция, которая отвечает — подходит одно под другое или нет.

## Правила (точные, из ТЗ)

| Шаблон | Что ловит | Что НЕ ловит |
|---|---|---|
| `order.created` | ровно `order.created` | `order.updated`, `Order.Created` |
| `order.*` | `order.created`, `order.created.v2` | `order`, `orders.created`, `order.` |
| `*` | вообще всё | — |
| `*.created` | ничего (не поддерживаем в v1) | — |

## Подготовка

```bash
git switch -c feat/20-event-matcher
mkdir -p internal/matcher
```

## Шаги

**1.** Объяви функции:

```go
package matcher

// Match проверяет, подходит ли тип события под шаблон подписки.
func Match(eventType, pattern string) bool { return false }

// MatchAny возвращает true, если тип подходит хотя бы под один шаблон.
func MatchAny(eventType string, patterns []string) bool { return false }
```

**2. Сначала напиши тесты** — здесь это особенно удобно, потому что таблица случаев уже дана в ТЗ. Перенеси её в код:

```go
func TestMatch(t *testing.T) {
	tests := []struct {
		eventType string
		pattern   string
		want      bool
	}{
		{"order.created", "order.created", true},
		{"order.created", "order.*", true},
		{"order.created.v2", "order.*", true},
		{"order", "order.*", false},          // ⚠️ сам префикс не подходит
		{"orders.created", "order.*", false}, // ⚠️ не спутать order. и orders
		{"order.", "order.*", false},         // после точки пусто
		{"anything", "*", true},
		{"order.created", "*.created", false}, // не поддерживается
		{"Order.Created", "order.created", false}, // регистр важен
		{"order.created", "", false},
		// ...добавь остальные из ТЗ, минимум 15 штук
	}

	for _, tc := range tests {
		t.Run(tc.eventType+"|"+tc.pattern, func(t *testing.T) {
			if got := Match(tc.eventType, tc.pattern); got != tc.want {
				t.Errorf("Match(%q, %q) = %v, хотели %v",
					tc.eventType, tc.pattern, got, tc.want)
			}
		})
	}
}
```

**3.** Реализуй по алгоритму:

1. Шаблон ровно `*` → `true`.
2. Шаблон заканчивается на `.*` → взять префикс до `.*`, проверить что тип начинается с этого префикса **плюс точка**, и что после точки есть хотя бы один символ.
3. Иначе — обычное сравнение строк.
4. `*` в середине или начале → `false`.

Пригодятся `strings.HasSuffix`, `strings.HasPrefix`, `strings.TrimSuffix`, `len`.

## ⚠️ Две ошибки, которые совершают все

**Ошибка 1.** Проверить только префикс без учёта точки:
```go
strings.HasPrefix(eventType, strings.TrimSuffix(pattern, "*"))
```
Тогда `orders.created` совпадёт с `order.*`, потому что `orders.created` начинается с `order`. Тест `{"orders.created", "order.*", false}` это ловит.

**Ошибка 2.** Не проверить, что после точки что-то есть. Тогда `order.` пройдёт под `order.*`, хотя не должен.

Обе ошибки ловятся тестами — если ты честно перенёс таблицу из ТЗ.

## ✅ Готово, когда

- [ ] Обе функции реализованы
- [ ] Минимум 15 тест-кейсов, включая все каверзные из ТЗ §6.4
- [ ] Покрытие 100%
- [ ] `make lint` зелёный

# B3. signing — HMAC-подпись

**Уровень:** L2 · **Время:** 4–5 часов · **Спецификация:** `docs/TZ.md` §6.2

Задача посложнее двух предыдущих. Возьми её **после** backoff или matcher.

## Что нужно сделать простыми словами

Получатель вебхука должен убедиться: запрос пришёл от нас, а не от постороннего, кто узнал его URL. Для этого мы «опечатываем» каждый запрос отпечатком, который может сделать только тот, кто знает общий секрет.

🧠 **Как работает HMAC.** Есть общий секрет (строка), известный нам и получателю. Мы берём тело запроса, перемешиваем его с секретом по алгоритму HMAC-SHA256 и получаем отпечаток — 64 символа. Кладём в заголовок. Получатель делает ровно то же самое своим секретом и сравнивает. Подделать отпечаток, не зная секрета, нельзя.

## Что именно подписываем

Не только тело, а склейку времени и тела:

```
подписываемая_строка = "1700000000" + "." + тело_запроса
подпись = hex( HMAC-SHA256(ключ=секрет, данные=подписываемая_строка) )
заголовок = "v1=" + подпись
```

🧠 **Зачем в подпись входит время.** Если подписывать только тело, злоумышленник, перехвативший наш запрос, сможет отправлять его повторно сколько угодно — подпись-то валидная. Это **replay-атака**. Со временем внутри получатель может сказать «этому запросу час, не принимаю».

## Подготовка

```bash
git switch -c feat/18-hmac-signing
mkdir -p internal/signing
```

## Шаг 1. Функция Sign

```go
package signing

// Sign возвращает готовое значение заголовка X-Hookline-Signature.
func Sign(payload []byte, secret string, ts time.Time) string
```

Алгоритм:
1. `strconv.FormatInt(ts.Unix(), 10)` — время в секундах строкой.
2. Склеить: `timestamp + "." + string(payload)`.
3. `mac := hmac.New(sha256.New, []byte(secret))`, затем `mac.Write(...)`, затем `mac.Sum(nil)`.
4. `hex.EncodeToString(...)`.
5. Вернуть с префиксом `"v1="`.

Импорты: `crypto/hmac`, `crypto/sha256`, `encoding/hex`, `strconv`, `time`.

## Шаг 2. Проверь себя по готовым векторам

В ТЗ §6.2 есть таблица с реальными посчитанными значениями. Это твой эталон: если совпало — реализация верна.

```go
func TestSign_ТестовыеВекторы(t *testing.T) {
	ts := time.Unix(1700000000, 0)

	tests := []struct {
		secret  string
		payload string
		want    string
	}{
		{"whsec_test_secret_1", `{"hello":"world"}`,
			"v1=40c946df3c6d5ff57d5d5ac21da91fa8116451adb4674feb3efe1e535c6577cf"},
		{"whsec_test_secret_1", `{}`,
			"v1=3cc6d220bd6d001d0f1931d315cb1765435a39bb810cde4e05e23a2b6d71a945"},
		{"whsec_test_secret_1", ``,
			"v1=1255ce5be0b18d90cb33658a5bd4895f474de17cd78fe3fd952061be13ae7830"},
		{"whsec_test_secret_2", `{"hello":"world"}`,
			"v1=bedbfdf6ab28c696d800ba48448f9d219823e158a61213d24bbcfa99c4b088e1"},
		// остальные — из ТЗ §6.2
	}

	for _, tc := range tests {
		got := Sign([]byte(tc.payload), tc.secret, ts)
		if got != tc.want {
			t.Errorf("Sign(%q, %q):\n получили %s\n хотели   %s",
				tc.payload, tc.secret, got, tc.want)
		}
	}
}
```

Обрати внимание на векторы 1 и 4: одно и то же тело с разными секретами даёт **совершенно разный** отпечаток. Это лавинный эффект — свойство криптографических хэш-функций.

## Шаг 3. Функция Verify

```go
func Verify(payload []byte, sigHeader, tsHeader, secret string,
            now time.Time, tolerance time.Duration) error
```

Алгоритм:
1. Распарсить `tsHeader` в число (`strconv.ParseInt`). Не число → `domain.ErrInvalidSignature`.
2. Проверить возраст: если **модуль** разницы между `now` и временем из заголовка больше `tolerance` → `domain.ErrSignatureExpired`.
   ⚠️ Именно модуль: запрос «из будущего» тоже подозрителен.
3. Проверить, что `sigHeader` начинается с `v1=`, отрезать префикс. Нет префикса → `ErrInvalidSignature`.
4. Посчитать ожидаемую подпись тем же способом, что в `Sign`.
5. Сравнить через **`hmac.Equal`**.
6. Не совпало → `ErrInvalidSignature`, иначе `nil`.

## ⚠️ Критическая грабля: сравнение подписей

**Только `hmac.Equal`. Никогда `==`, `strings.Compare` или `bytes.Equal`.**

🧠 Почему. Обычное сравнение строк выходит на первом различающемся символе. Значит, время ответа зависит от того, сколько символов совпало. Замерив время тысячи раз, атакующий подбирает подпись символ за символом. Это **timing attack**. `hmac.Equal` сравнивает за постоянное время независимо от данных.

## Шаг 4. Остальные тесты

Из ТЗ §6.2:
1. Все векторы совпадают.
2. `Verify` принимает то, что создал `Sign`.
3. Отвергает: чужой секрет, изменённое тело, испорченную подпись, подпись без `v1=`.
4. Отвергает старый timestamp и timestamp из будущего.
5. Не паникует на мусоре: `""`, `"v1="`, `"abc"`, очень длинная строка.
6. Покрытие 100%.

## ⚠️ Ещё одна грабля

**Подписывай сырые байты тела**, ровно те, что уйдут в сеть. Если распарсить JSON в структуру и сериализовать обратно — порядок полей и пробелы могут измениться, и у получателя подпись не сойдётся. Всегда работай с `[]byte`.

- [ ] Все 6 векторов из ТЗ совпадают байт в байт

# B4. cmd/sink — тестовый приёмник

**Уровень:** L1 · **Время:** 3 часа · **Спецификация:** `docs/TZ.md` §6.12

**Зачем.** Нужен «фальшивый получатель», которым можно управлять: пусть отвечает 500, пусть зависает на 15 секунд. Без него нечем проверять доставку и ретраи. **Пользоваться будут все**, так что задача важная и заметная.

## Что должно уметь

```
POST /hook                      → отвечает 200
POST /hook?status=500           → отвечает 500
POST /hook?delay=15s            → отвечает после паузы (проверка таймаутов)
POST /hook?status=500&delay=2s  → и то и другое
GET  /received                  → JSON-список всего полученного
POST /reset                     → очистить список
```

## Подготовка

```bash
git switch -c feat/21-test-sink
mkdir -p cmd/sink
```

## Шаги

**1. Структура для хранения.** Всё полученное храним в памяти:

```go
type received struct {
	Method    string            `json:"method"`
	Headers   map[string]string `json:"headers"`
	Body      string            `json:"body"`
	Timestamp time.Time         `json:"timestamp"`
}

type store struct {
	mu    sync.Mutex   // ⚠️ обязателен: HTTP-хендлеры бегут в разных горутинах
	items []received
}
```

⚠️ **Мьютекс здесь обязателен.** Каждый HTTP-запрос обрабатывается в своей горутине. Без мьютекса два одновременных запроса испортят срез — детектор гонок это поймает.

**2. Хендлер `/hook`:**
- прочитать тело (`io.ReadAll`), не забыть `defer r.Body.Close()`;
- собрать заголовки в map;
- сохранить в store под мьютексом;
- прочитать `r.URL.Query().Get("delay")` — если задан, распарсить через `time.ParseDuration` и подождать;
- прочитать `status`, распарсить `strconv.Atoi`, по умолчанию 200;
- ответить этим кодом, залогировать факт получения.

**3. Хендлер `/received`:** отдать `json.NewEncoder(w).Encode(items)` под мьютексом.

**4. Хендлер `/reset`:** очистить срез.

**5. Порт** брать из переменной окружения `SINK_PORT` (по умолчанию 9090).

**6. Проверь руками:**

```bash
go run ./cmd/sink &
curl -X POST 'localhost:9090/hook' -d '{"test":1}'          # → 200
curl -X POST 'localhost:9090/hook?status=500' -d '{}'        # → 500
curl -X POST 'localhost:9090/hook?delay=3s' -d '{}'          # ждёт 3 сек
curl localhost:9090/received                                  # список
```

## ⚠️ Грабли

- Забыть мьютекс → `go test -race` покажет гонку.
- Забыть `defer r.Body.Close()` → утечка.
- Не обработать кривой `?delay=абв` → паника. Ошибку парсинга просто игнорируй, бери значение по умолчанию.

- [ ] Все шесть маршрутов работают
- [ ] `?status=` и `?delay=` реально влияют на ответ
- [ ] Доступ к хранилищу под мьютексом, `-race` чист

- [ ] Есть тест хотя бы на `?status=` и `/received`

## Шаг 4. Graceful shutdown (важная привычка)

Сервер должен корректно останавливаться по Ctrl+C и по сигналу от Docker:

```go
ctx, stop := signal.NotifyContext(context.Background(),
	os.Interrupt, syscall.SIGTERM)
defer stop()
```

Дальше: запускаешь сервер в горутине, ждёшь `<-ctx.Done()`, вызываешь `srv.Shutdown(...)` с отдельным контекстом и таймаутом из `HTTP_SHUTDOWN_TIMEOUT`.

🧠 Зачем это уже сейчас: если заложить сразу, потом не придётся переделывать. А без этого Docker будет убивать процесс жёстко, обрывая запросы на середине.

Уровень и формат (`text`/`json`) читай из `LOG_LEVEL` и `LOG_FORMAT`.

# C2. #10 — Миграция 0001

**Уровень:** L1–L2 · **Время:** 4 часа · **Спецификация:** `docs/TZ.md` §5

**Зачем.** Создать все таблицы проекта. Пока их нет, никто не может работать с базой.

## Что такое миграция

SQL-файл, который меняет структуру базы. Хранится в репозитории, применяется по порядку. Так у всех в команде одинаковая структура, и её изменения проходят через ревью, как код.

Мы используем **goose**. Формат файла:

```sql
-- +goose Up
-- здесь SQL, создающий таблицы

-- +goose Down
-- здесь SQL, откатывающий изменения
```

`Up` применяется при обновлении, `Down` — при откате. Комментарии `-- +goose` обязательны, по ним goose разделяет части.

## Шаг 1. Установи goose

По тому же принципу, что и линтер — локально в `./bin`, не глобально:

```bash
GOBIN=$(pwd)/bin go install github.com/pressly/goose/v3/cmd/goose@latest
./bin/goose --version
```

Потом это стоит добавить в Makefile как цель, но сначала убедись, что работает руками.

## Шаг 2. Создай файл миграции

```bash
mkdir -p migrations
touch migrations/0001_init.sql
```

Имя важно: номер в начале задаёт порядок применения.

## Шаг 3. Пиши SQL по ТЗ §5

В ТЗ §5.2–5.7 приведены **все таблицы целиком**, с типами и ограничениями. Бери оттуда, ничего не выдумывай. Порядок создания важен из-за внешних ключей:

```
apps → endpoints → subscriptions
     → events → messages → attempts
```

Нельзя создать `endpoints` раньше `apps` — он на него ссылается.

**Не забудь индексы** (ТЗ §5.6) — их три, и они не для красоты:

```sql
CREATE INDEX idx_messages_due ON messages (next_attempt_at)
    WHERE status = 'pending';
```

🧠 **Что такое частичный индекс** (`WHERE` в конце). Через месяц в таблице будут миллионы доставленных сообщений и лишь сотни ждущих. Обычный индекс тащил бы все строки. Частичный индексирует только те, что подходят под условие — и остаётся маленьким и быстрым.

## Шаг 4. Секция Down

Удаление в **обратном** порядке относительно создания:

```sql
-- +goose Down
DROP TABLE IF EXISTS attempts;
DROP TABLE IF EXISTS messages;
DROP TABLE IF EXISTS events;
DROP TABLE IF EXISTS subscriptions;
DROP TABLE IF EXISTS endpoints;
DROP TABLE IF EXISTS apps;
```

Наоборот нельзя: нельзя удалить `apps`, пока на него ссылается `endpoints`.

## Шаг 5. Применяй и проверяй

```bash
make up      # поднять базу

export GOOSE_DRIVER=postgres
export GOOSE_DBSTRING="$DATABASE_URL"
./bin/goose -dir migrations up

# посмотреть, что получилось:
make psql
```

Внутри psql:
```
\dt              -- список таблиц
\d messages      -- структура таблицы messages
\di              -- список индексов
\q               -- выйти
```

**Обязательно проверь откат:**

```bash
./bin/goose -dir migrations down    # должно снести всё без ошибок
./bin/goose -dir migrations up      # и накатить обратно
```

## Шаг 6. Впиши в Makefile

Заглушку `migrate` замени на реальный вызов goose. Заодно добавь `migrate-down` и автоскачивание goose по тому же приёму «цель-файл», что сделан для линтера.

## ⚠️ Грабли

- **Статусов сообщения четыре**, не пять: `pending`, `in_flight`, `delivered`, `dead`. В старой версии ТЗ был ещё `failed` — его больше нет. Сверься с ТЗ §5.6.
- **Уже применённую миграцию менять нельзя.** goose помнит, что она накатана, и второй раз не применит. Если ошибся до мержа — откати (`down`), поправь, накати снова. После мержа — только новая миграция `0002_...`.
- `timestamptz`, а не `timestamp` — нам нужны часовые пояса.
- Не забудь `UNIQUE (app_id, idem_key)` в `events` — на этом ограничении держится вся защита от дублей.

- [ ] Все шесть таблиц из ТЗ §5 созданы
- [ ] Три индекса из §5.6 на месте
- [ ] `goose up` работает на чистой базе
- [ ] `goose down` откатывает без ошибок, `up` накатывает снова

# C3. #8 и #9 — ADR (архитектурные записки)

**Уровень:** L1 · **Время:** 2 часа на каждую

## Что такое ADR и зачем

ADR (Architecture Decision Record) — короткая записка на полстраницы: «мы решили делать так, потому что…». Хранится в `docs/adr/`, заводится через PR и ревьюится как код.

🧠 **Зачем это нужно на самом деле.** Через два месяца никто не вспомнит, почему очередь сделана в Postgres, а не через Redis. Придёт новый человек, спросит, и без ADR ответ будет «ну как-то так вышло». А ещё раздел «Альтернативы» из ADR — это буквально готовый ответ на собеседовании, когда спросят «а почему не Kafka?».

## Структура (шаблон в `docs/adr/README.md`)

```markdown
# ADR-0003: Очередь сообщений на FOR UPDATE SKIP LOCKED

**Статус:** принято
**Дата:** 2026-07-25

## Контекст
Какая задача стоит, какие ограничения.

## Решение
Что именно решили. Конкретно, с деталями.

## Альтернативы
Что ещё рассматривали и почему отвергли. ← самая ценная часть

## Последствия
Что стало проще, что сложнее, чем платим.
```

## ADR-0003: очередь

Основа уже написана в `docs/TZ.md` §6.5 — там и claim-запрос, и инварианты. Твоя работа: собрать это в формат ADR и **осмысленно заполнить «Альтернативы»**.

Что обязательно раскрыть:
- схема таблицы `messages` и роль полей `next_attempt_at`, `locked_until`;
- сам claim-запрос с разбором, что делает `SKIP LOCKED`;
- механизм лиза и reaper: что происходит, когда воркер упал;
- семантика **at-least-once** и почему не exactly-once;
- альтернативы: Kafka, Redis, `SELECT FOR UPDATE` без `SKIP LOCKED`, `LISTEN/NOTIFY` — по каждой одно-два предложения, почему не она.

⚠️ Эта ADR — **самая важная бумага проекта**. Её читают все, и после её мержа любой участник должен уметь своими словами объяснить, что делает `SKIP LOCKED`. Это Exit-критерий фазы 0.

## ADR-0004: интерфейс Clock

Короче и проще. Суть: `time.Now()` в бизнес-логике запрещён, время приходит через интерфейс.

```go
type Clock interface {
	Now() time.Time
}
```

Что раскрыть:
- проблема: как протестировать «сообщение вернулось в очередь через 30 секунд», не ожидая реальные 30 секунд;
- решение: интерфейс + подменный `FakeClock` в тестах с методом `Advance`;
- правило: `time.Now()` разрешён только в `RealClock`;
- последствия: чуть больше кода, зато тесты мгновенные и не флакуют.

# Волна 2 — краткие ориентиры

Эти задачи ждут волны 1. Полные спецификации — в ТЗ, здесь только «что ждать и с чего начать».

## #13 queue — claim/ack/nack

**Ждёт:** #10 миграцию + #8 ADR. **Уровень L3, задача лида.**
**ТЗ §6.5.** Готовые SQL-запросы уже приведены в ТЗ, включая claim с `SKIP LOCKED`. Главное: время передавать **параметром**, а не писать `now()` в SQL, иначе тесты с фейковыми часами невозможны. Обязательны интеграционные тесты через testcontainers — их список в ТЗ.

## #15 ingest — приём событий

**Ждёт:** #10 миграцию + #11 скелет. **Уровень L2.**
**ТЗ §6.8 и §7.1.** Ключевое: идемпотентность реализуется **не** проверкой `SELECT` перед вставкой (при двух одновременных запросах оба увидят «нет такого»), а ловлей ошибки уникальности Postgres с кодом `23505`. Отвечать надо `202 Accepted`, а не 200 — это семантика «принял, обработаю потом».

## #17 delivery — HTTP-клиент

**Ждёт:** `signing`. **Уровень L2.**
**ТЗ §6.7.** Три вещи, которые легко забыть: переиспользовать **один** `http.Client` на весь пул (иначе кончатся сокеты), читать тело через `io.LimitReader` (иначе злонамеренный получатель отдаст гигабайт), обязательный `defer resp.Body.Close()`.

## api — HTTP-каркас и CRUD

**Ждёт:** #11 скелет. **Уровень L1–L2.**
**ТЗ §6.11 и §7.** Начни с каркаса: роутер, middleware (request_id → логирование → recover → auth, именно в таком порядке), единый формат ошибок с таблицей маппинга доменных ошибок в HTTP-коды. Только потом CRUD. DTO держи отдельно от доменных типов — иначе в JSON случайно улетит секрет эндпоинта.
